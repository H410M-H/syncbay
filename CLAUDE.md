# Syncbay — Agent Guide

Syncbay (`syncbay.app`) is a hybrid-compute PaaS. The **control plane** is a Next.js 16 App Router app (tRPC 11, Prisma 5 / PostgreSQL, NextAuth v4). It runs on Vercel. The **data plane** is a standalone runner daemon (`runner/`) that clones, builds and runs customer services on any Linux host, exposed through Cloudflare Tunnels.

## Commands

| Task | Command |
| --- | --- |
| Dev server | `npm run dev` |
| Prisma client | `npx prisma generate` |
| Type-check | `npm run typecheck` (`tsc --noEmit`) |
| Dead code | `npm run knip` (config: `knip.json`) |
| Lint | `npm run lint` |
| Production build | `npm run build` (prisma generate + `next build --webpack`) |
| Runner build / test | `cd runner && npm install && npm run build && npm test` |
| Focused verifications | `npm run test:fallback`, `test:tunnel`, `test:edge`, `test:email`, `test:db`, `test:terminal` (tsx scripts under `tests/`, mocked DB); `test:terminal-stateless`, `test:domains` (need `DATABASE_URL`; real Postgres, Docker, DNS stub); `test:observe` (real Postgres + runner); `test:deploy` needs a real `DATABASE_URL` and starts runner daemons on 41100/41101; `test:billing` (`TEST_DATABASE_URL`, optional `TEST_STRIPE_MOCK_URL`) and `test:r2` (optional `TEST_S3_ENDPOINT`/`TEST_S3_ACCESS_KEY_ID`/`TEST_S3_SECRET_ACCESS_KEY`, `TEST_DATABASE_URL`); `test:devops`, `test:query` (real Postgres via `TEST_DATABASE_URL`, real Redis via `TEST_REDIS_URL`); `test:projects` (real Postgres via `DATABASE_URL`, starts a runner daemon on 47100); `test:availability` (real Postgres, runner daemon on 49100); `test:admin` (real Postgres; staff console, enforcement, security fixes) |
| Runner DB provisioning | `cd runner && npm run test:provision` (real initdb/pg_ctl, redis-server, Docker postgres) |
| Runner deploys on Docker | `cd runner && npm run test:docker` (real Docker; needs the `node:20-bookworm-slim` and `postgres:16-alpine` images) |

All five gates (prisma generate, typecheck, knip, lint, build) must pass before a change is merged. CI enforces them in `.github/workflows/ci.yml`.

## Architecture map

### Orchestration — `src/lib/orchestrator/`
- **`engine.ts` → `executeDeployment()`.**
  - Loads service, variables and environment databases, resolves `${{ ref }}` variables (`src/lib/buildpack/resolver.ts`), claims the service's platform hostname, and dispatches the job to a runner driver.
  - **Hostnames** (`src/lib/domains/`): a service routes only its own `Domain` rows. `claimDefaultHostname()` gives the first service `<service>-<env>.syncbay.app` and a later same-named service a suffixed host; `resolveServiceHostnames()` / `primaryServiceHostname()` (pure, client-safe) are the only way to get a service's hosts. Never build a host from the service name.
  - **Zero downtime:** when another deployment of the service is ACTIVE (`findLiveRoute`), its route stays ACTIVE while this one builds and after this one fails. Only a service with nothing live is routed `BUILDING` → `DEPLOYING` → `FAILED` (`setInFlightRoutes`).
  - **Ports:** `Service.port` is the app's own listening port. The runner's host port is `Deployment.assignedPort`, and routing, the DB resolver and tunnel ingress read that. The engine writes `Service.port` only when the runner reports a detected `metadata.containerPort`.
  - Runtime detection (`src/lib/buildpack/detector.ts`, nixpacks plans) happens on the runner. The engine relays every log line to `logEventBus` (`src/lib/telemetry/event-bus.ts`) and classifies it as `stderr` (`[build:error]`, `[app:error]`, `Error:` …), `system` (`[pipeline]`, `[runner]`, `[health]` … prefixes) or `stdout`.
  - After an `ACTIVE` result it probes `/health`, then `/`, on the allocated port (through `RUNNER_URL` + `x-target-port` for webhook runners). The probe is skipped only when the runner reports `metadata.simulated`, or for a pull-mode runner without `RUNNER_URL` (it probed itself).
  - Call sites never fire-and-forget: they call `scheduleDeployment()` (`schedule.ts`), which writes a `DeploymentJob` row and runs the engine in `after()` (routes export `maxDuration = 300`). Polling stops after `DEPLOY_POLL_BUDGET_MS` (240 s) and hands off; `recoverStaleDeployments()` (`recovery.ts`, called from the cron) resumes lapsed orchestrator leases (`options.resume`), requeues expired runner leases and fails legacy stuck deployments.
  - If the engine's own probe fails after the runner reported ACTIVE, it stops that instance before failing the deployment.
  - On ACTIVE, `onDeploymentActive()` (`lifecycle.ts`) records `assignedPort`/`runnerDriver`, marks older live deployments `SUPERSEDED` and stops their instances, and reports the PR preview status. `lifecycle.ts` also implements real pause / delete / restart / rollback (`stopServiceInstances`, `restartServiceInstance`, `rollbackToDeployment`). `stopServiceInstances` is the single stop path: scale-to-zero's `stopServiceToSleep()` delegates to it. Every stop, restart and rollback ends with `requestTunnelReload()`. The cron reaches `recoverStaleDeployments()` through `src/lib/crons/recovery-hook.ts` (direct import).
  - No invented commit SHAs: HEAD is resolved through Octokit (`resolveHeadCommitSha`) or left null.
  - Failed remote dispatches (for example Cloudflare HTTP 530) fall back to the local driver. `RUNNER_FALLBACK_LOCAL=false` (default `true`) or `RUNNER_FORCE_REMOTE=true` disables this. An `AuthenticationError` never falls back.
  - When status polling reports `exitCode`, the engine appends it to the recorded error (`… (exit code N)`).
  - A failure is persisted in `Deployment.errorMessage` (cleared on ACTIVE); routers prefer it over the in-process `logEventBus.getError()`. The engine awaits `logEventBus.flush()` before returning.
  - `src/lib/buildpack/knip-analyzer.ts` is Syncbay's built-in static analysis of customer repos. It is separate from the repo's own `knip` gate.
- **`runner-driver.ts` (`getRunnerDriver()`).** Picks a driver from the explicit type, then `RUNNER_DRIVER` (`webhook` | `ssh` | `queue` | `local` | `mock`), then `RUNNER_URL`:
  - `signRequest()` signs `${ts}.${nonce}.${METHOD}.${path}.${body}` with HMAC-SHA256 into `X-Syncbay-Signature: sha256=<hex>`, `X-Syncbay-Timestamp` and `X-Syncbay-Nonce` (16 random bytes, hex). `path` is the API pathname, and GET requests sign the job id as the body. Every retry is re-signed with a fresh timestamp and nonce.
  - `resolveRunnerSecret()` reads `RUNNER_WEBHOOK_SECRET` → `RUNNER_SECRET` → `SYNCBAY_WEBHOOK_SECRET`. With `NODE_ENV=production` and no secret it throws `AuthenticationError`; only dev falls back to a default secret. A production webhook driver without `RUNNER_URL` throws `RunnerConfigError`. Both carry the actionable "Runner not configured: …" message from `runner-config.ts`.
  - `runner-config.ts`: `getRunnerConfigStatus()` → `{ mode: webhook|ssh|queue|local|simulated, urlHost, secretConfigured, problem? }` (mirrors `getRunnerDriver()`, never returns secret values); `assertRunnerConfigured()` is the deploy preflight; `checkRunnerHealth()` probes the unauthenticated `GET {RUNNER_URL}/health` (3 s). `deployment.trigger`/`redeploy`, `project.redeployAll`, the wizard and `POST /api/v1/deployments` preflight before creating any row (tRPC `PRECONDITION_FAILED` via `src/server/runner-preflight.ts`, REST 412 `RUNNER_NOT_CONFIGURED`). `scheduleDeployment()` (webhooks, crons) only logs the problem.
  - `lifecycle.driverFor()` falls back to the local driver only when no remote runner is configured and the instance did not run on one; otherwise it throws `RunnerConfigError`, so stop/restart/pause fail instead of reporting a false "stopped". `stopServiceInstances()` resolves every hosting driver before it marks anything, and `assertInstancesControllable()` lets bulk actions refuse up front.
  - Webhook and SSH requests retry with exponential backoff and jitter (500 ms·2^n, capped at 8 s, 4 attempts). Webhook retries on transient Cloudflare/gateway statuses and network errors; SSH retries on exit 255 (connection failure).
  - Drivers log through `emitLog()`. It passes lines to `params.onLog` when one is given (the engine's handler publishes to `logEventBus`); otherwise it publishes to `logEventBus` directly.
  - `WebhookRunnerDriver`: HTTP to the runner daemon.
  - `SshRunnerDriver`: runs containers on a remote host over SSH (`RUNNER_SSH_*`), with `RUNNER_SECRET` exported in the remote command environment.
  - `QueueRunnerDriver` (`RUNNER_QUEUE_MODE=pull`): queues the job in `DeploymentJob` (`job-queue.ts`). Runners claim it with HMAC `POST /api/v1/runner/jobs/claim` (`FOR UPDATE SKIP LOCKED`) and report logs, heartbeats and the result to `POST /api/v1/runner/jobs/:id/events`. Stop and restart become control jobs routed to the hosting runner.
  - `LocalRunnerDriver`: imports `runner/src/pipeline.ts` in-process (local dev / single host). `RUNNER_DRIVER=mock` uses it with `MockPipelineExecutor`.
- **`src/lib/tunnel/tunnel-config.ts`.**
  - `generateTunnelConfig()` produces YAML and `generateTunnelConfigJson()` produces the Cloudflare `PUT /accounts/{acct}/cfd_tunnel/{id}/configurations` body (`{ config: { ingress } }`). `writeTunnelConfig()` writes atomically (temp file + rename).
  - `reloadTunnel()` PUTs the config through `CloudflareApiClient.updateTunnelConfiguration()` when `CLOUDFLARE_TUNNEL_ID`, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` are all set. Otherwise it writes `TUNNEL_CONFIG_FILE` and runs `TUNNEL_RESTART_COMMAND` (default `systemctl restart cloudflared`), because cloudflared has no SIGHUP reload.
  - `src/lib/tunnel/tunnel-sync.ts` → `requestTunnelReload(reason)` rebuilds the full ingress table from the DB (non-paused services with an ACTIVE deployment, their own platform host and ACTIVE domains → `http://127.0.0.1:<assignedPort>`, catch-all `TUNNEL_FALLBACK_SERVICE`), debounced (`TUNNEL_RELOAD_DEBOUNCE_MS`, 300 ms), serialised with `pg_advisory_xact_lock`, never throws, and is a no-op without a tunnel (`CLOUDFLARE_TUNNEL_ID` + API creds, or + `TUNNEL_CONFIG_FILE`). Called after deploy ACTIVE (engine), deployment delete, and domain verify/delete; call it from any new stop/pause/delete path.
- **`pr-manager.ts`.** Handles GitHub `pull_request` webhooks:
  - Creates an ephemeral `pr-<n>` environment, service and `<svc>-pr-<n>.syncbay.app` domain, with scale-to-zero (`idleTimeoutSecs: 1800`).
  - Posts a `pending` `syncbay/preview` commit status and comment; the engine updates both to success/failure (`reportPreviewDeploymentStatus`). Tokens come from env, the triggering user or a workspace member, never an unrelated account.
  - Sleeps or destroys the environment when the PR is closed.

### API — `src/server/`
- `trpc.ts` defines `publicProcedure` and `protectedProcedure` (a session is required). Routers are composed in `root.ts`. Every mutation must use `protectedProcedure` and check workspace membership.
- `routers/deployment.ts` → `redeploy`:
  - `rebuild: false` is the fast redeploy. It reuses the previous successful build record and keeps caches.
  - `rebuild: true` is the clean rebuild. It creates a new Build and sends `cleanBuild: true`. The runner then purges `node_modules`, `dist`, `.next`, `build`, `out`, `.turbo` and `.cache`, and passes `--no-cache` to Docker/Nixpacks.
- `routers/project.ts`: project names are unique per workspace among non-deleted projects (trimmed, case-insensitive, under a per-workspace advisory lock; `src/lib/projects/project-names.ts`). A duplicate is `CONFLICT` with `error.data.details.existingProjectId` (`ErrorDetails` cause → `trpc.ts` formatter); `POST /api/v1/projects` answers 409. `update` renames; `redeployAll` / `pauseAll` / `resumeAll` loop the shared helpers in `src/lib/orchestrator/service-actions.ts` (`redeployFromDeployment`, `setServicePaused`, also used by `deployment.redeploy`, `service.setPaused` and the v1 route) and return per-service results; `delete` (OWNER/ADMIN, `confirmName`) stops every service's instances, releases its domains, marks services and project deleted and reloads the tunnel. There is no restore. `list` adds `counts` (latest deployment per service), `lastDeployedAt` and `myRole`.
- UI building blocks: `src/components/ui/action-menu.tsx` (accessible menu button, portal-positioned), `confirm-dialog.tsx` (native `<dialog>`, typed-name confirmation or one input) and `toast.tsx`. The new-project wizard preflights the runner, reuses the project it created on retry and, after a later failure, opens it with `?setupError=` (`src/components/dashboard/project-setup-notice.tsx`).
- The REST API lives at `src/app/api/v1/*` (token auth via `src/lib/api/auth-token.ts`, OpenAPI at `/api/v1/openapi.json`).

### Runner daemon — `runner/`
- `src/index.ts` (`RunnerDaemon`):
  - Unauthenticated: `/health` and `/api/tunnel/status`.
  - HMAC-protected: `POST /api/builds`, `GET /api/builds/:id[/logs]` (JSON or SSE), `POST /api/containers/:id/stop`, `POST /api/containers/:id/restart` (re-launches from the kept launch spec on the same port; also revives a stopped instance for rollback), `GET /api/metrics/:containerId` and `POST /api/traffic/drain`.
  - `src/traffic.ts` counts every proxied request per target port and UTC minute (requests, 2xx/3xx/4xx/5xx, `errors` = upstream network failures answered 502, body bytes in/out, latency to response headers: sum/max and <50/<200/<1000/≥1000 ms). `POST /api/traffic/drain` (verified by `verifySignedRequest()`, POST payload = body) returns the buckets since the last drain, attributed to `containerId`/`jobId`/`deploymentId` through the job ↔ port map, and resets them (at-most-once). The store is process-wide (`getDefaultTrafficStats()`), bounded to 50k buckets.
  - Any request with `x-target-port` is proxied to the app before the daemon's own routes.
  - `RUNNER_QUEUE_MODE=pull` + `SYNCBAY_API_URL` starts `JobPullConsumer` (`src/job-consumer.ts`, `RUNNER_ID`, `RUNNER_POLL_INTERVAL_MS`); its claim/events calls are signed with the same nonce scheme.
  - Signatures must match `signRequest()`'s canonical string (`runner/src/request-auth.ts`). Every signed request, of any method, is single-use: accepted nonces are cached for the ±5 min window, so a replay gets 401. New routes must verify through `verifySignedHeaders()` / `verifySignedRequest()` (which consume the nonce), not the pure `verifySignature()`.
  - Query-string `sig`/`ts`/`nonce` is accepted only on the SSE route `GET /api/builds/:id/logs` with `Accept: text/event-stream`, and it is bound to that path.
  - `src/metrics.ts` serves `/api/metrics/:id` (verified by `verifySignedRequest()`, GET payload = pathname, like `services.ts`): `docker stats --no-stream` for containers, `/proc/<pid>/stat` + `status` summed over the process group for `proc_<pid>` native apps (no network counters for those).
  - `GET /api/builds/:id` returns `exitCode` and `simulated`.
  - The secret comes from `RUNNER_SECRET`. In production the daemon refuses to start without one.
  - `/health` reports `version` (`runner/src/version.ts`) and `startedAt`. Bump the version with every runner change the control plane relies on, together with `MIN_RUNNER_VERSION` in `src/lib/orchestrator/runner-config.ts`; `checkRunnerHealth()` sets `outdated` and the dashboard tells the operator to update the host.
  - `src/build-hints.ts` → `ensureBuildx()` (at startup and before each build): if `docker buildx version` fails, it downloads buildx (`RUNNER_BUILDX_VERSION`) into `~/.docker/cli-plugins`, unless `RUNNER_AUTO_INSTALL_BUILDX=false`. `/health` reports `toolchain: { docker, buildx, nixpacks }`; `checkRunnerHealth()` passes it through and the dashboard warns when buildx is missing.
  - `src/redact.ts` → `redactSecrets()` strips URL userinfo and GitHub tokens from every log line and error. The control plane mirrors it in `src/lib/telemetry/redact.ts` (`logEventBus.publish`/`recordError`, engine and job-queue `errorMessage`).
  - Any other request is reverse-proxied to the service port in `x-target-port`.
  - After a deploy it registers routes back to the control plane (`/api/v1/services/edge-register`) and adds `<host> → http://127.0.0.1:<port>` tunnel ingress. A stop removes it.
- `src/pipeline.ts`:
  - The build payload's `volumes` (`[{ id, name, mountPath, sizeGb }]`, from `src/lib/orchestrator/volume-payload.ts` in `engine.ts`) are mounted by `src/volumes.ts`: `-v syncbay-vol-<id>:<mountPath>` for Docker (relative paths under `/app`), or a bind dir `<state>/volumes/<id>` for native processes exposed as `SYNCBAY_VOLUME_PATH` / `VOLUME_<NAME>_PATH` (relative mount paths are symlinked into the app dir). `sizeGb` is not enforced.
  - `src/launch.ts` holds the launch helpers: `shq()` (shell-quote one argument), `tailText()`, `containerEnv()`, `parseListeningPorts()`, `pickNodeVersion()`, `Semaphore`.
  - Environment values never appear on a command line or in a log: `docker run -e KEY` / `nixpacks build --env KEY` read them from the CLI's process environment. `git` runs without service variables. User commands are passed through `shq()`.
  - Builds: at most `RUNNER_MAX_CONCURRENT_BUILDS` (2) at once. A failed build's error is the end of its output (`tailText`). Nixpacks projects that pin no Node version (or an open range such as `>=18`) build with Node `RUNNER_DEFAULT_NODE_VERSION` (22).
  - Start-up of a Docker instance: up to `RUNNER_HEALTH_TIMEOUT_MS` (120 s). A container that exited or restart-loops fails the deploy with `docker logs`. If the app does not listen on the expected port, `detectContainerPort()` reads `/proc/net/tcp` (fallback: EXPOSE and common ports, probed on the bridge IP), re-creates the container with the host port mapped to the real port and reports `containerPort`. Only-loopback listeners produce a "bind 0.0.0.0" hint. Container names are unique per deployment.
  - `options.rewriteEnv` (wired to `RunnerServices.rewriteEnv`) points URLs of databases on this runner at the private address (`src/db-network.ts`).
  - `BuildPipeline` clones, detects the strategy (Docker → Nixpacks → native), builds, then starts the app on a port from `PortManager` (`src/port-manager.ts`, range 10000–60000). A job that asks again while its previous instance still listens (a fast redeploy reuses the build id as job id) gets a new port. `PipelineResult.exitCode` is 0 on success, otherwise the exit code of the failing step or of the crashed app.
  - A fast redeploy (`cleanBuild: false`) reuses an existing clone with `git fetch` + `git checkout -f FETCH_HEAD`.
  - A clean rebuild re-clones, purges `node_modules dist .next build out .turbo .cache` (logging each path) and passes `--no-cache`.
  - A 25-line `stderr` ring buffer (split into lines) captures startup crashes. If the process exits before `/health` answers, the job fails with that trace and the exit code.
  - `MockPipelineExecutor` is used only when `RUNNER_DRIVER=mock`, or when serverless (`VERCEL` / `AWS_LAMBDA_FUNCTION_NAME`) without `RUNNER_URL`. It is also a fallback, with a warning, when git is missing.
- `src/tunnel-driver.ts` runs `cloudflared` (token, quick-tunnel or config-file mode), a local proxy, or an SSH reverse tunnel.
  - Config-file mode (`TUNNEL_CONFIG_FILE` + `CLOUDFLARE_TUNNEL_ID`, optional `TUNNEL_CREDENTIALS_FILE`) runs `cloudflared tunnel --config <file> run`.
  - In that mode `updateIngress()` rewrites the YAML atomically (`src/tunnel-config.ts`, a mirror of the control plane generator) and restarts cloudflared. Unknown hosts fall through to the daemon.
- Imports inside `runner/` use explicit `.ts` extensions. They run under Node type-stripping or `tsx`, and `tsc` rewrites them to `.js` in `dist/`.

### Edge routing
- `src/lib/edge/service-registry.ts` is a two-tier registry mapping a hostname to `{ targetPort, status, upstreamUrl, isLocal }`. Hosts are normalised case-insensitively.
  - **L1** is a per-process Map. `ACTIVE` routes live 15 s, every other status 2 s (so `BUILDING` → `ACTIVE` shows up quickly), and misses are negatively cached for 5 s.
  - **L2** is an `L2Store` chosen by `getL2Store()`:
    - `UpstashRestStore`: plain `fetch` to `UPSTASH_REDIS_REST_URL` with Bearer `UPSTASH_REDIS_REST_TOKEN`. It stores JSON at `syncbay:edge:route:<host>` (`SET … EX` 7 d) and keeps an index set `syncbay:edge:routes`.
    - `DbResolveStore`: read-only, backed by `resolveServiceRouteFromDb()` in `src/lib/edge/resolve.ts`, the same lookup `/api/v1/services/edge-resolve` uses. It routes to the newest ACTIVE deployment (its `assignedPort`), even behind a newer building or failed one. Platform hosts use the subdomain heuristics. Custom domains need an exact, `ACTIVE` `Domain` row.
    - `MemoryStore`: used when neither is configured. When Upstash and `DATABASE_URL` are both set, an Upstash miss falls through to the DB.
  - Writers (`engine.ts`, the `domain` router, `edge-register`) call `registerServiceRouteAsync` / `removeServiceRouteAsync`, which write through to L2 and never throw.
  - Readers call `resolveServiceRoute`: a fresh L1 hit, otherwise L2 hydration, with lookups single-flighted per host. If L2 errors, the stale L1 entry is served.
  - The sync `registerServiceRoute` / `getServiceRoute` / `removeServiceRoute` are L1-only and kept for tests and in-process callers.
- `src/proxy.ts` is the Next 16 Proxy. It runs on the Node runtime and exports `proxy`; `middleware.ts` is deprecated.
  - **Bypass list:** `/api/trpc`, `/api/auth`, `/api/webhooks`, `/api/deployments`, the `edge-resolve`/`edge-register`/`wake` APIs and `/service-preview` are never rewritten.
  - **Control-plane hosts pass through:** `syncbay.app`, `www.`, `cname.`, `localhost`, any IP, `*.vercel.app`, and the `NEXTAUTH_URL` / `VERCEL_*` hosts.
  - **Service hosts:** `*.syncbay.app`, `*.localhost`, and any other host only if it resolves as a registered route (a custom domain).
  - It rewrites `ACTIVE` services to their upstream, or to `RUNNER_URL` with `x-target-port` unless `isLocal`. It answers `/health` with 200/503/502 and sends non-active services to the splash page.
  - WAF (`src/lib/edge/waf.ts`, after the `/health` branch): the host's enabled `WafRule`s (IP_ALLOW > IP_BLOCK (IPv4/IPv6 CIDR) > GEO_BLOCK (`x-vercel-ip-country`/`cf-ipcountry`) > PATH_BLOCK (glob) > RATE_LIMIT) return 403/429. Rate limits count per rule+client IP in one-minute Upstash windows (`INCR`/`EXPIRE` over REST) or an in-process sliding window. Hits are batched into `WafRule.hitCount/lastHit*`.
  - Canary (`src/lib/edge/canary.ts`, in the ACTIVE branch): an ACTIVE `CanaryConfig` splits traffic by weight between `stableUpstreamUrl` and `canaryUpstreamUrl`, pinned by the `sb_canary=<configId>.<variant>` cookie (24 h). After a rollback, stable is served only while the live route still points at the canary upstream. Routed counts are batched into `CanaryConfig`.
  - Both read `src/lib/edge/edge-policy.ts`: host → service (exact `Domain` row or the `<svc>-<env>` default host) plus rules and canary, cached 15 s per instance. No `DATABASE_URL` or a DB error means no filtering (fail open).
  - For `ACTIVE` routes it calls `recordServiceRequest(host)` (`src/lib/scale/activity.ts`, via `event.waitUntil`): debounced 30 s per host, written to Upstash `syncbay:edge:last:<host>` when configured, else `Service.lastRequestAt`. WAF-blocked requests return before this and are not counted.
- `/api/v1/services/edge-register` (POST/DELETE) accepts `{ hostname, targetPort, status, upstreamUrl, isLocal }`.
  - Auth is Bearer `RUNNER_SECRET` / `SYNCBAY_WEBHOOK_SECRET`.
  - In production it returns 401 when neither secret is set.
- `src/app/service-preview/[subdomain]/page.tsx` is the cold-start splash.
  - An unknown status renders as `BUILDING`.
  - It streams build logs over SSE from `/api/deployments/:id/logs/stream` (session + workspace membership required; anonymous visitors get 401 and no logs). The route (`src/lib/telemetry/log-stream.ts`) replays `DeploymentLog` rows, then follows the in-process bus plus a DB tail every 2 s (cross-instance), and proxies the runner's signed `GET /api/builds/:id/logs` SSE when neither has lines. It never synthesises history. It also emits `event: status` when the deployment status changes. Each connection ends after `STREAM_MAX_MS` (270 s) with `retry: 1000`; log lines carry `id: <seq>` and a reconnect resumes after `Last-Event-ID`. The metrics stream ends at the same limit.
  - It polls `/health` every 1.5 s, stops probing on success, and reloads into the live app.
  - The wake button POSTs to `/api/v1/services/wake`. The caller must be a workspace member session or send Bearer `RUNNER_SECRET`. The endpoint re-runs the sleeping service's latest deployment through `executeDeployment` (via `after()`) and returns 202.

### Observability, usage and scale-to-zero (crons)
- `logEventBus` (`src/lib/telemetry/event-bus.ts`) keeps a 1000-line ring buffer per deployment as a cache and batches every line into `DeploymentLog` (`src/lib/telemetry/log-store.ts`; flush at 250 ms or 200 lines, retried with backoff, only when `DATABASE_URL` is set). No `.runner_logs` files.
- `/api/deployments/:id/metrics/stream` (session + membership) and `metrics.live` read the runner live (`fetchContainerMetrics()`; in-process collector when there is no `RUNNER_URL` and not serverless), else the newest `MetricSample`. `metrics.historical` buckets stored samples (`date_bin`). No random or sine data.
- `vercel.json` crons, both `GET` with `Authorization: Bearer $CRON_SECRET` (`src/lib/crons/cron-auth.ts`, timing-safe; unset secret is allowed only outside production):
  - `/api/cron/tick` (every minute, `maxDuration` 300; resumed deployments poll for 200 s): `recoverStaleDeployments()` from `src/lib/orchestrator/recovery.ts` through a webpack `require.context` hook (`src/lib/crons/recovery-hook.ts`), plus `sampleActiveServices()` → `MetricSample` and `collectTraffic()` (`src/lib/telemetry/traffic-sampler.ts`) → `TrafficSample` (signed drain via `runnerFetch()`; local driver drains the in-process store; attribution by deployment id, then `cfContainerId`, then a unique ACTIVE `assignedPort`; same-minute drains are summed with `ON CONFLICT`).
  - `/api/cron/sweep` (every 15 min): `sleepIdleServices()` (`src/lib/scale/idle-sleeper.ts`), `writeUsageRecords()` and `enforceSpendingCaps()` (`src/lib/usage/metering.ts`), `runMonthlyInvoicingIfDue()` (`src/lib/billing/invoicing.ts`: previous month's invoices, only on the 1st from 02:00 UTC, idempotent), and retention (logs 30 d, samples 35 d, traffic 35 d).
- Always-on: `scaleToZero` defaults to false. `/api/cron/tick` also runs `wakeAlwaysOnServices()` (`src/lib/scale/always-on.ts`): an always-on, unpaused service whose newest SLEEPING deployment has nothing ACTIVE or in flight beside it is started again (skipped over the spending cap; 3 per run).
- Idle sleep: services with `scaleToZero` whose latest deployment is ACTIVE and whose last activity (last request, deploy completion, docker inbound traffic) is older than `idleTimeoutSecs` are stopped via the runner driver, marked SLEEPING, routed to the splash and dropped from the tunnel ingress via `requestTunnelReload()` (`src/lib/scale/service-control.ts`).
- Usage: one `UsageRecord` per service, resource and completed hour (`CPU_ACTIVE_SECONDS` = vCPU-seconds, `MEMORY_GIB_HOURS`, `EGRESS_GB`; upsert on the new unique key). `workspaceUsage` is month-to-date (UTC). At 80 % of `spendingCapCents` owners/admins get the usage-warning email, at 100 % every running service is paused and they get the billing alert (once per month each, `Workspace.usageWarnedAt` / `spendCapReachedAt`). The wake endpoint answers 402 while the cap is reached.
- `npm run test:observe` (`tests/verify-observability.ts`) needs a migrated Postgres (`TEST_DATABASE_URL` or `DATABASE_URL`) and starts a real runner daemon on port 42110.
- Dashboard analytics: `src/server/routers/analytics.ts` (`overview`, `deploymentTimeline`, `recentActivity`, `traffic`; membership-scoped) over `src/lib/analytics/` — service state from the latest deployment per non-deleted service (`isPaused` wins), deploy success = ACTIVE/SLEEPING/SUPERSEDED vs FAILED/CRASHED, resources = newest `MetricSample` (≤ 10 min) per live service, traffic error rate = (5xx + network errors) / requests. Runner status comes from `getRunnerConfigStatus()` / `checkRunnerHealth()` in `src/lib/orchestrator/runner-config.ts`. UI: `src/components/analytics/` (polls 15 s while the tab is visible) and hand-rolled SVG charts in `src/components/charts/`. `npm run test:analytics` (`tests/verify-analytics.ts`) needs a migrated Postgres and starts a real runner on `RUNNER_PORT` (default 48110).

### Staff console — `/admin`
- Staff are users with an active `StaffMember` row (`role`: SUPER_ADMIN | ADMIN | SUPPORT | MODERATOR | BILLING | VIEWER). Customer roles (`WorkspaceMember`) grant nothing here.
- `src/lib/admin/permissions.ts` is the role × permission matrix (pure, client-safe: `can()`, `gateFor()`, `permissionsOf()`). Gates are `allow`, `reason` (written reason ≥ 8 chars) or `confirm` (reason + typing the target's name).
- `src/server/staff-procedure.ts` → `staffProcedure(permission)`: non-staff get NOT_FOUND, missing permissions FORBIDDEN plus a DENIED audit row; `ctx.staff.audit()` and `ctx.staff.assertConfirmed(name, required?)`. Every admin mutation audits. Router: `src/server/routers/admin.ts` (explicit `select`s only; never env values, DB URLs, tokens, password hashes; billing only for `billing.read`).
- `src/lib/admin/staff.ts`: `getStaffIdentity()` reads the role from the DB on every call. `SUPER_ADMIN_EMAILS` pins super admins, only for accounts with a GitHub/Google `Account` linked. `recordStaffEvent()` writes `StaffAuditEvent` (append-only: a DB trigger rejects UPDATE/DELETE; never delete it in retention or tests).
- Enforcement (`src/lib/admin/enforcement.ts`, `guards.ts`): workspace suspension and service take-down pause services through `setServicePaused` and set `Workspace.suspendedAt` / `Service.moderationLockedAt`. `assertServiceMayRun()` is called by the engine (all deploy entry points), `setServicePaused` (resume) and the wake endpoint; always-on skips them. Suspended users (`User.suspendedAt`) are refused at sign-in, by `protectedProcedure` (30 s cache) and by API tokens.
- Public abuse intake: `POST /api/v1/abuse` (`src/lib/admin/abuse-intake.ts`: strict schema, honeypot `website`, `renderedAt` ≥ 2 s, 10/h per IP, de-dupe) and the `/report-abuse` page; reports link to the service owning the host's `Domain` row.
- Security invariants: `src/lib/edge/forward-headers.ts` strips NextAuth/staff cookies from every request the edge forwards to a customer app (the runner proxy strips them too). User rows shown to other users use `PUBLIC_USER_SELECT` (`src/lib/users/public-user.ts`).

### Other modules
- Auth: `src/lib/auth.ts` (Google, GitHub with `repo` scope, credentials/bcrypt; JWT sessions with the Prisma adapter). `resolveGithubToken()` (`src/lib/github.ts`) picks a GitHub token for a project: env, triggering user, workspace owners, members; a token GitHub answers 401 for is cleared and skipped. The engine and `pr-manager` use it, so cron/webhook deploys of private repos work. In production `src/lib/auth-cookies.ts` scopes the session cookie to `AUTH_COOKIE_DOMAIN` (default `.syncbay.app` when `NEXTAUTH_URL` is on syncbay.app; `none` disables) so service hosts send it to the wake endpoint.
- Email: `src/lib/email/` (Resend + React Email templates; it logs instead of sending when `RESEND_API_KEY` is unset).
- Domains and Cloudflare: `src/lib/domain-service.ts`, `src/lib/tunnel/cloudflare-api.ts`.
  - `verifyDomainDetailed()` resolves `TXT _syncbay-challenge.<host>` and the CNAME to `CLOUDFLARE_CNAME_TARGET` (or flattened A records) with `node:dns/promises`; missing records keep `VERIFYING`. With `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ZONE_ID` the custom hostname and certificate must also be `active`. Nothing is simulated in production (`CloudflareNotConfiguredError`), and live API errors are thrown, not simulated.
  - A verified domain copies the service's live route (`src/lib/edge/domain-upstream.ts`). `purgeEdgeCache()` calls Cloudflare `purge_cache` when zone + token are set, else returns `configured: false`. The static POP list is illustrative (`illustrative: true`).
- Managed DBs and buckets: `src/lib/database-provider.ts`, `src/lib/storage-provider.ts`.
  - With `RUNNER_URL` set, the runner provisions the database (`runner/src/services.ts`: `/api/databases`). `RUNNER_DB_MODE` (`auto` | `docker` | `native` | `mock`): Docker runs `postgres:16-alpine`/`redis:7-alpine`/`mysql:8`; without Docker, `runner/src/native-db.ts` runs native Postgres (`initdb`/`pg_ctl`, data under `RUNNER_STATE_DIR/databases/<id>`) and Redis (`redis-server` with a 0600 config), as `RUNNER_NATIVE_DB_USER` when root. Health uses `pg_isready`/`redis-cli ping`/`mysqladmin ping`; delete stops the server and removes data. MySQL needs Docker. Connection URLs carry `RUNNER_DB_HOST` (for external tools); apps on the same runner get them rewritten to the Docker bridge gateway or 127.0.0.1 (`RUNNER_DB_INTERNAL_HOST` overrides). Docker databases are re-discovered from their `syncbay.managed-db` label after a runner restart. `RUNNER_DB_PORT_RANGE` gives databases their own host-port range. Without a runner a mock `sb-db-*` instance is created. `DatabaseInstance.status` tracks PROVISIONING → ACTIVE/UNHEALTHY/FAILED/DELETING.
  - Buckets are real Cloudflare R2 buckets (`src/lib/storage-provider.ts`). Create/delete go through the R2 API (`src/lib/storage/r2-api.ts`, `/accounts/{CLOUDFLARE_ACCOUNT_ID}/r2/buckets`, Bearer `CLOUDFLARE_API_TOKEN`). Delete empties the bucket first. Object listing and presigned GET/PUT use `@aws-sdk/client-s3` at `https://<acct>.r2.cloudflarestorage.com` with `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`. `R2_ENDPOINT` overrides the endpoint for any S3-compatible server; buckets are then created through S3 `CreateBucket`. With no keys every remote call throws `StorageNotConfiguredError` (fail closed). Buckets are private (`publicUrl: null`) and no per-bucket credentials are minted.
  - `<NAME>_URL` and `DATABASE_URL` (Postgres) or `REDIS_URL` (Redis) are persisted on existing services when the DB is created. `engine.ts` also merges them in at deploy time (`applyDatabaseEnv`) without overriding user keys. Delete removes rows still pointing at the DB. Signed runner calls go through `src/lib/runner-client.ts`.
- Billing (Stripe): `src/lib/billing/`.
  - No card data ever reaches Syncbay. Cards are added through `billing.createSetupIntent` → Stripe Elements `confirmSetup` in the browser (`src/components/billing/stripe-card-setup.tsx`) → `billing.confirmSetupIntent`. That call verifies the SetupIntent and PaymentMethod belong to the workspace's Stripe customer, then stores only the `pm_…` id plus brand, last4 and expiry. Every billing input schema is `.strict()`, so any unexpected key (a card number, for example) is a 400.
  - Saved cards are listed from Stripe and the local rows are reconciled against that list. Top-ups are PaymentIntents. Credits are granted exactly once, when Stripe reports `succeeded` (via the webhook or `billing.syncTopUp`); a conditional status flip in one transaction guarantees this.
  - `buildMonthlyInvoices(periodStart)` (`invoicing.ts`) prices `UsageRecord` with `pricing.ts` (the single rate card, also used by `metering.ts` and the usage page), applies prepaid credits and issues a finalized Stripe Invoice. It is idempotent on `(workspaceId, periodKey)`. `pdfUrl` is the Stripe hosted invoice or receipt URL.
  - `POST /api/webhooks/stripe` verifies `Stripe-Signature` on the raw body with `STRIPE_WEBHOOK_SECRET` and returns 503 when unconfigured. It handles `payment_intent.*`, `setup_intent.succeeded` and `invoice.paid`/`payment_failed`, idempotent per event id (`StripeEvent`).
  - Without `STRIPE_SECRET_KEY` billing is explicitly "not configured": mutations return PRECONDITION_FAILED and the UI disables payments. `STRIPE_API_BASE` points the SDK at stripe-mock or another emulator.
- DevOps engines (`src/lib/devops/`, router `devops.ts`), all DB-backed:
  - `cron-engine.ts` (`CronJob`/`CronRun`, full 5-field UTC parser) and `cron-runner.ts` → `runDueCronJobs(now)`: claims due jobs with a conditional update (advances `nextRunAt`, sets a `lockedUntil` lease), calls the service over HTTP (registry upstream, via `RUNNER_URL` + `x-target-port` when remote, else `https://<svc>-<env>.syncbay.app`) with per-attempt timeout and retries on network errors/timeouts/5xx/429, then records a `CronRun`.
  - `waf-engine.ts` (`WafRule` CRUD + pure evaluation), `canary-engine.ts` (`CanaryConfig`; `evaluateCanaryHealth` rolls back above the 5xx threshold using the canary deployment's `TrafficSample` counts (5xx + network errors) or `options.errorCounts`; with no traffic recorded it returns INSUFFICIENT_DATA with a null rate and reports the canary's sample count). `vercel-migrator.ts` writes `CronJob`/`WafRule` rows.
  - `ai-diagnostics.ts` and `auto-tuner.ts` are rule-based heuristics (`method: "heuristic"`); they suggest, never apply.
- Query Studio (`src/lib/query-studio/engine.ts`, router `query-studio.ts`): real `pg`/`mysql2`/`ioredis` connections to `DatabaseInstance.connectionUrl`. Read mode (default) is a single statement in a READ ONLY transaction that is rolled back, 10 s statement timeout, 1000-row cap; Redis read mode allows read commands only. Write mode needs OWNER/ADMIN; Safe Mode blocks destructive SQL and FLUSHALL/FLUSHDB. Introspection uses `information_schema` (SQL) or `SCAN`/`TYPE` (Redis). Simulated `sb-db-*` instances are refused.
- Web shell: `src/components/dashboard/web-shell.tsx` → `POST /api/services/:id/terminal` (create, or `{sessionId,input}`) + SSE `/api/services/:id/terminal/stream`, with session auth and workspace membership. The control plane is stateless: `sessionId` is a token signed with `TERMINAL_TOKEN_SECRET` (`src/lib/shell/terminal-token.ts`, `{sid, mode, runnerSessionId, serviceId, userId, exp}`; production returns 503 without the secret). Runner sessions proxy to runner `/api/terminals` (`docker exec -i <container> sh` or `sh` in the job workspace, under `script -qfc`). Without a runner the simulated `src/lib/shell/web-shell.ts` keeps cwd, env overrides, history and the masked buffer in a `TerminalSession` row (optimistic `version` writes; the SSE stream polls it; 10 min idle). Output masks `isSecret` values and URL credentials.

## Deployment
- Vercel builds with `npm run vercel-build` (`scripts/vercel-build.mjs`): prisma generate → `prisma migrate deploy` (production only; `DIRECT_URL` falls back to `DATABASE_URL`; P3005 or any migrate failure aborts the build; `SKIP_DB_MIGRATE=1` skips) → `next build --webpack`. Every schema change must ship as a migration under `prisma/migrations/`.
- Self-hosted runner: `deploy/alibaba-ecs/` (docker-compose: `runner` from `runner/Dockerfile`, multi-arch via `TARGETARCH`, host network + `/var/run/docker.sock`; `caddy` with automatic TLS for `RUNNER_DOMAIN` → `127.0.0.1:8080`). Only 80/443 are public. Control plane: `RUNNER_URL=https://<RUNNER_DOMAIN>`, same `RUNNER_SECRET`, `RUNNER_DRIVER=webhook`.

## Conventions
- Next.js 16 differs from older versions. Read `node_modules/next/dist/docs/` before using framework APIs.
- Keep `tests/**` out of the app's tsconfig. Tests run via `tsx` with a mocked `globalThis.prisma`.
- Branding is **Syncbay** / `syncbay.app` only.
- Every new env var goes into `.env.example`.
